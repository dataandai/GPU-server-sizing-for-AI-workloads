Core Engines

Two engines, one answer

ENGINE 01
⬡
Monte Carlo Simulation

Instead of single fixed estimates, the Monte Carlo engine draws thousands of samples from probability distributions for token counts, concurrency, and batch sizes — producing a realistic statistical envelope of memory and performance outcomes.

01 Input processing — model config, hardware profile, workload type and token distributions are ingested and validated
02 Token sampling — random draws from prompt, output and concurrency distributions per iteration
03 VRAM computation — model weights + KV-cache + active compute buffers summed per GPU
04 OOM detection — flags iterations that exceed GPU memory limits and accumulates risk probability
05 Statistical output — p50 / p95 / p99 VRAM, OOM %, KV-cache saturation, hardware recommendation
ENGINE 02
◈
Workload Simulation Engine

Models full production environments: Poisson request arrivals, FIFO queuing, SLA enforcement, and multi-stage pipelines — giving end-to-end latency, throughput, and GPU utilization distributions before you deploy.

01 Scenario loading — pipeline stages, runtime family, deployment profile and simulation horizon
02 Calibration anchors — real benchmark data matched to each pipeline stage for accuracy
03 Stochastic trials — random arrival rates, token counts and SLA requirements applied per trial
04 Queue simulation — M/M/1 and M/M/c models, drop policy, wait time accumulation
05 Aggregated output — p50/p95/p99 latency, RPS, SLA compliance rate, GPU utilisation, TCO
ENGINE 03
▦
Catalog System

A live-updated catalog of hardware, models, and software stacks powers all simulations with accurate specs and performance priors.

HW Hardware catalog — GPU VRAM, bandwidth, node configs (2/4/8 GPU), network and storage specs
ML Model catalog — dynamic Hugging Face model loading with architecture parameters and memory models
SW Software stacks — vLLM, TGI, quantisation methods, attention backends, MIG and bare-metal profiles
ENGINE 04
∑
Mathematical Models

Every estimate is grounded in first-principles memory accounting, calibrated inference timing, and standard queuing theory — not rule-of-thumb heuristics.

M Memory — weights (params × dtype), KV-cache (tokens × layers × heads × dtype), active compute
P Performance — calibrated inference timing, multi-GPU communication overhead modelling
Q Queuing — M/M/1 and M/M/c arrival-service models for wait time and saturation analysis
$ Cost — GPU acquisition cost, power draw × tariff, full TCO breakdown

Mathematical Foundation

First-principles memory & performance accounting

Model Weight Memory
VRAMw = params × bytes_per_dtype

Parameter count multiplied by the dtype byte-width (FP32 = 4 B, FP16 = 2 B, INT8 = 1 B). Quantisation reduces this linearly.

KV-Cache Memory
VRAMkv = T × L × Hkv × d × 2 × bytes

Tokens × layers × KV heads × head dimension × 2 (key+value). Scales linearly with context length. For GQA/MQA models (Llama 3, Mistral, Qwen…) Hkv ≪ Hq, reducing cache memory by 4–8×.

Active Compute Buffer
VRAMact = B × S × A_complexity

Batch size × sequence length × a layer-dependent attention complexity factor. This is a placeholder approximation — the real value is architecture-specific and varies per activation. Used for conservative headroom estimation only.

Queuing Theory
Wq = λ / (μ(μ − λ))  ·  W = 1/(μ − λ)

M/M/1 model: Wq is mean wait time in queue; W is total time in system (queue + service). λ = arrival rate, μ = service rate. Extended to M/M/c for multi-GPU pools.

Hardware Cost
TCO = GPU$ × count + P_w × t × tariff

GPU acquisition cost plus energy spend over the operational period. MIG and bare-metal profiles adjust utilisation denominators.

OOM Risk
Poom = |{i : VRAMi > cap}| / N

Fraction of Monte Carlo trials where total VRAM exceeds the GPU's physical capacity. Drives hardware upgrade recommendations.

Accuracy & Trust

Calibrated, validated, honest

Calibration

All performance priors are anchored to real inference benchmarks across GPU SKUs and model families. Calibration coverage scores tell you exactly how much of each estimate is data-driven versus extrapolated.

Validation Rules

Every simulation input is validated against physical GPU memory limits, positive-value constraints, and logical distribution consistency. Physical impossibilities are rejected before any compute runs.

Error Handling

Missing calibration data is filled from conservative defaults and flagged explicitly. Uncalibrated configurations receive a visible warning so you always know when an estimate is more uncertain.

Multi-language Support

Language-mix scaling factors adjust throughput and memory estimates for multilingual deployments, reflecting real tokenizer and compute differences across scripts and languages.
